### C2. `&` (address-of) laxness (`xc.m` `expression()`)

Current `elseif token == And` silently no-ops for any non-lvalue, diverging
from xc.c's `bad address of` error. Fix with an "is-array" flag:

- [x] Add a global `unit_was_array` to the parser globals (`xc()` and
      `expression()`).
- [x] Clear it at the start of the unit section and at binary-loop entry of
      `expression()`; set it in the Id-unit array branch (`idtype >= 4096`)
      only.
- [x] Rewrite the `And` branch — load-check **first** (handles `&*arr`:
      deref ends in LC/LI, so the drop fires before the flag is consulted),
      then the array no-op, else fail:
      ```
      if text(ti+1) == LC || text(ti+1) == LI
          ti = ti - 1;                 % drop the load; ax = address
          expr_type = expr_type + PTR;
      elseif ~unit_was_array
          fail(sprintf('%d: bad address of', line));
      end                              % array name: address already in ax
      ```
- [x] Tests — three positive corpus files + one negative (split from the
      plan's single-file sketch so each exit code is checkable):
      - `pp_addrof.c` → exit 42: `&a[0]` on an array element (LC/LI drop);
      - `pp_addrof2.c` → exit 78: `&a` on a bare **global** array name;
      - `pp_addrof3.c` → exit 34: `&a` on a bare **local** array name (LEA);
      - `pp_badaddrof.c` → errors with `bad address of` (try/catch + strfind).
      Existing `&` corpus (p3_pointer, p5_*, p6_memset) unchanged and green.
      Residual (pre-existing, out of scope): `&<literal>` whose final operand
      value coincidentally equals 9/10 (e.g. `&9`) is still accepted via the
      LC/LI check — a 1-based-indexing artifact on invalid C only.

## Notes / decisions

- **No structural changes**: all fixes are targeted; no parser/VM redesign.
  The `&` flag approach was chosen over a last-instruction heuristic because
  `IMM` is shared by literals, strings, enums, and sizeof (ambiguous), while a
  unit-level flag is exact.
- **The clone quirk behind Phase B** (script local functions not resolvable by
  name in `-batch`) belongs in the gitignored runtime bug report — it is a
  runtime limitation, not a port bug.
- **Negative tests** (expected errors) use the existing `try/catch` +
  `strfind(e.message, ...)` pattern from run_tests group 2.
- **Reference parity**: none of the Phase C changes alter accepted-program
  semantics except the zero-divisor guard (previously silent 0) and the `&`
  error (previously silently accepted non-lvalues) — both edge cases the
  reference rejects/crashes on.
